Блок 2. Экспертиза

Задание 5. Прыжок через этаж

Спросите у игрока get("x") — а x живёт этажом ниже, внутри position! → runtime error: json object has no key 'x'. Письмо знакомое, причина новая: get смотрит только на своём этаже — этажи не проваливаются и не просвечивают. Диагноз в тетрадь: «ключа нет, хотя он в файле ЕСТЬ → посмотри, на каком он этаже». Лесенка — не бюрократия, а маршрут.

Задание 6. Этаж — не число

player.get("position").to_int() → json value is object, expected int. Коллекция писем типов из №3 пополнилась словом object: этаж нельзя распаковать как число — сначала to_object(), потом внутрь. Симметрично проверьте to_string() на этаже — семейство единое, диагноз один: смотри, ЧТО лежит, прежде чем объявлять тип.

Задание 7. Дверь, а не копия

Открытие книги — экспериментом. Получите этаж: json.Object pos = player.get("position").to_object(); — и поправьте его: pos.set("x", json.Value(999));. А теперь напечатайте родителя: player.to_json() — x изменился и там! Полученный этаж — не копия, а дверь в тот же этаж: правишь за дверью — меняется дом. Родня Бобиков из ООП и ловушки tmp: объект — это ссылка, и врезку урока №6-JSON вы прочтёте через книгу. Пока — двойной вывод в тетрадь: это опасность (хотел копию — а изменил оригинал) и инструмент (править глубину без пересборки — з.10 покажет всю мощь).

Задание 8. Лесенка в одну строку

Стиль-эксперимент: золото из трёхэтажной крепости (fortress.json!) — двумя способами: лесенкой с переменными (три строки, каждый этаж назван) и цепочкой: fortress.get("tower").to_object().get("chest").to_object().get("gold").to_int() — одна строка, работает (проверено!). Обсудите честно: цепочка короче, лесенка читается и отлаживается (упало — известно, на каком этаже!). Правило вкуса: два этажа — цепочка уместна, три и глубже — лесенка добрее к будущему себе.

Ключи и переменные — разные миры: связывает их только ваш get.

Минутка из внешнего мира. Матрёшка как формат данных

Это не задание — делать ничего не нужно. Просто любопытное из большого мира, читается за минуту.

Когда программисты всего мира объясняют вложенность, они говорят «nested» — «гнездовой». Но самая точная метафора — русская: матрёшка. Кукла в кукле, коробка в коробке — и, что важно, каждая внутренняя кукла — полноценная кукла: у неё есть всё то же, что у внешней. Так и вложенный объект: у него свои ключи, свой get, свой to_json — он не «кусочек» родителя, а объект в полных правах. Настоящие конфиги живут матрёшками в три-четыре этажа: у игры — раздел graphics, в нём — раздел shadows, в нём — quality и distance. А самые глубокие матрёшки мира — в веб-данных: ответ сервера крупного сайта бывает этажей в десять (и где-то там программист со вздохом пишет десятую ступеньку лесенки — или, по нашему правилу вкуса, десять именованных переменных).

Задание 19 ⭐⭐. Великая миграция

Инженерная работа взрослых — миграция данных. В раздатке flat_hero.json — герой «плоского стиля»: pos_x, pos_y, stat_strength, stat_intellect — все этажи расплющены в префиксы (так писали, пока не знали вложенности, — узнаёте себя две книги назад?). Программа-мигратор: прочитать плоского → собрать структурного (name; position{x, y}; stats{strength, intellect} — данные те же, архитектура новая!) → записать hero_structured.json → показать оба файла: было 5 ключей в куче, стало 3 этажа со смыслом. Это рефакторинг ДАННЫХ — как рефакторинг кода в №8-canvas, но предмет — файл: поведение (данные) не меняется, структура — хорошеет. Настоящие студии гоняют такие миграции на миллионах сейвов при каждом крупном обновлении — и пишут их ровно так, как вы сейчас: читалка старого, сборщик нового, сверка. Кто напишет обратный мигратор (структурный → плоский) и прогонит туда-обратно с полным совпадением — тот сдал экзамен по круговороту данных.
