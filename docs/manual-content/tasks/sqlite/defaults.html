Задание 5. Двойная Мира

Задание 6. Смертельное удобство

DROP TABLE IF EXISTS — удобная строка, к которой мы привыкли с первых книг. Прочувствуйте её вес: наполните таблицу двадцатью строками (конвейером из №7!), запустите программу с DROP-прологом и убедитесь: всё исчезло без единого вопроса. Урок предупреждает дословно: «в настоящем проекте она безвозвратно удалит и таблицу, и все её строки». Правило: DROP-пролог хорош для учебных экспериментов, идемпотентность — для настоящих программ; они решают одну задачу («запускаться много раз») противоположными способами — стереть прошлое или ужиться с ним.

Задание 7. Явный NULL сильнее умолчания

Тонкая ловушка. Колонка level INTEGER DEFAULT 1; вставка через параметр с bind("level", null) — что окажется в базе? Единица? Нет: NULL (проверено!). Логика железная: DEFAULT срабатывает, когда значение не указано вовсе; а вы указали — и указали «неизвестно». Разница между «промолчать» и «сказать "не знаю"» — ровно та, что в №6 отделяла NULL от пустой строки. Практический вывод: если программа читает необязательный ввод и пустоту превращает в null — DEFAULT-ы молча перестанут работать; чтобы они сработали, поле нужно не передавать вообще (два разных запроса или INSERT без этой колонки).

Задание 8. Схему никто не сверял

Ещё тише и опаснее. Создайте таблицу с четырьмя колонками; затем выполните CREATE TABLE IF NOT EXISTS players (name TEXT) — с совсем другой схемой. Ошибки нет, всё «хорошо» — а таблица осталась старой (проверьте через sqlite_master из №1!). Вывод: IF NOT EXISTS проверяет только имя, а не устройство. Что это значит на практике: если вы поменяли схему в коде, а база старая — программа будет работать со старой таблицей и падать на несуществующих колонках. Именно из-за этого взрослые проекты не полагаются на IF NOT EXISTS, а ведут миграции (№9 з.19!) — журнал применённых изменений.

Минутка из внешнего мира. Кнопка, которую можно нажимать дважды

Это не задание — делать ничего не нужно. Просто любопытное из большого мира, читается за минуту.

Слово идемпотентность пришло из математики: операция идемпотентна, если её повторение ничего не меняет (умножение на единицу, взятие модуля, «поставить на паузу»). В программировании это стало требованием к целым классам систем. Знакомая ситуация: вы нажали «оплатить», связь пропала, вы нажали ещё раз — списалось дважды? В хорошей системе — нет: платёжный запрос несёт ключ идемпотентности, и сервер, увидев повтор, отвечает «уже сделано» вместо второго списания. Так же устроены очереди сообщений (доставка «хотя бы один раз» означает, что дубли будут — и обработчик обязан их пережить), инструменты развёртывания вроде Ansible («приведи систему в такое состояние» — а не «выполни эти шаги») и ваши миграции из девятой книги. Правило индустрии простое: сеть ненадёжна, повторы неизбежны — значит, повтор должен быть безвредным. Ваша программа из первого задания уже соответствует стандартам, которые в больших компаниях пишут в регламентах.

Задание 15. Опасное удобство: OR REPLACE

Специя сверх урока — и ловушка индустриального уровня. INSERT OR IGNORE при конфликте UNIQUE тихо пропускает вставку (задето 0 — удобно для «добавь, если нет»!). А вот INSERT OR REPLACE притворяется удобством: он удаляет старую строку и вставляет новую. Испытайте: у Миры было 340 монет; выполните INSERT OR REPLACE INTO players (name, level) VALUES ('Мира', 99) — уровень стал 99, а монеты обнулились в DEFAULT (проверено!). Никакой ошибки. Диагноз: REPLACE — это не UPDATE; всё, чего вы не перечислили, теряется. Правило: обновлять — UPDATE (он трогает только названные колонки), а OR REPLACE применять лишь там, где строка действительно перезаписывается целиком.

Задание 16. Идемпотентный сидинг

Возвращаемся к скриптам №9 (раздатка) критически: setup_guild.sql начинается с DROP — значит, при повторе он сносит мир (для учебной базы нормально, для рабочей — катастрофа), а seed_extra.sql без DROP при повторе упрётся в UNIQUE-имена. Напишите третий скрипт — идемпотентный сидинг: CREATE TABLE IF NOT EXISTS + INSERT OR IGNORE для каждой строки (з.15!). Прогоните трижды: первый раз создаёт и наполняет, второй и третий — не меняют ничего (счётчики COUNT одинаковы). Скрипт, который можно применять всегда, — вершина инженерной аккуратности этой книги.

Задание 18 ⭐. Синхронизатор

Задача из мира настоящих систем: есть массив «эталонных» данных в программе (десять товаров с ценами) и есть таблица в базе, которая могла устареть. Программа-синхронизатор приводит базу к эталону: чего нет — добавить, что отличается — обновить (UPDATE только изменившихся: сравнить цену перед правкой!), чего нет в эталоне — пометить (или удалить — решите и обоснуйте). Отчёт: «добавлено 2, обновлено 3, лишних 1, без изменений 4». Запустите дважды — второй раз всё в графе «без изменений». Это ровно то, что делают инструменты развёртывания из минутки: не «выполни шаги», а «приведи в состояние».

Задание 19 ⭐⭐. Версии схемы

Финал темы идемпотентности — самообновляющаяся база. Служебная таблица schema_version (version INTEGER); программа при запуске: читает версию (нет таблицы — считает версией 0 и заводит её), затем по очереди применяет недостающие обновления: v0→v1 создаёт players, v1→v2 добавляет колонку nickname (ALTER TABLE из №9!), v2→v3 создаёт items и наполняет их, — каждое обновление в транзакции вместе с записью новой версии (тонкость из №9 з.19: применение и отметка атомарны!). Прогоны: на чистой базе — все три шага; повторно — «база актуальна, версия 3»; а теперь допишите четвёртое обновление и запустите — применится только оно. Вы построили механизм, который в больших системах называется автомиграцией: программа сама доводит любую базу — пустую, старую, свежую — до нужного состояния. Кто добавит проверку «версия базы новее, чем знает программа» с честным отказом («база из будущего — обновите приложение») — тот предусмотрел сценарий, о котором забывают даже взрослые команды.
