Блок 1. Соединение

Практика с преподавателем

Задание 1. Числа становятся именами

Собираем у доски пример урока — сначала схему со связью:

CREATE TABLE guilds (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT UNIQUE
);

CREATE TABLE players (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT,
    guild_id INTEGER,
    FOREIGN KEY (guild_id) REFERENCES guilds(id)
);

Затем — соединение:

SELECT players.name, guilds.title AS guild
FROM players
JOIN guilds ON players.guild_id = guilds.id
ORDER BY players.name;

Проговорите четыре вещи. Первая: зачем делить — название гильдии хранится один раз, а в игроках лежит только номер: переименовали гильдию — поменялась одна строка, а не тысяча (эхо №12: id не меняется, имена меняются!). Вторая: JOIN ... ON — «соединяй строки, у которых номер совпадает с номером». Третья: имена таблиц перед колонками (players.name) — потому что колонки с одинаковыми именами есть в обеих. Четвёртая — честное предупреждение урока: SQLite не проверяет связь — вставить игрока в несуществующую гильдию можно, и никто не пикнет (з.7 покажет, и это не баг, а особенность).

Самостоятельная практика

Задание 2. Гильдия рассказывает

guild.db, первый JOIN на живых данных: покупки с именами героев — purchases JOIN players ON purchases.player_id = players.id — печать «День 1: Мира — покупка №5». Сравните вывод с той же задачей из №3 (з.14 — «день 1: игрок 3 купил товар 7»): числа заговорили. Вексель одиннадцати книг оплачен.

Задание 3. И товары тоже

Тройное соединение: purchases + players + items — «День 1: Мира купила "Зелье от прокрастинации" за 150» (эталон подтверждает!). Схема соединений: покупка знает номер героя и номер товара, и каждый номер приводится к своей таблице отдельным JOIN-ом. Три таблицы, две связки — вся вселенная гильдии в одном запросе.

Задание 4. Короткие имена

Псевдонимы: FROM purchases AS pu JOIN players AS p ON pu.player_id = p.id — тот же запрос, но читается легче (а p.name AS hero даёт понятное имя колонке в результате). Перепишите з.3 с псевдонимами и сравните длину. Правило вкуса: псевдоним — одна-две буквы, но узнаваемые (p — players, i — items); называть таблицы a, b, c — способ через месяц не понять собственный запрос.

Блок 2. Экспертиза

Задание 5. Пропавшая Ника

Ключевая особенность обычного JOIN: в примере урока Ника с guild_id = NULL не попадает в результат — для неё нет подходящей строки в guilds. Соберите такую таблицу (герой без гильдии) и убедитесь: в JOIN его нет. Диагноз: JOIN показывает только пары; тот, у кого пары нет, молча исчезает из отчёта. Это самая частая причина фразы «а почему в отчёте меньше людей, чем в базе?».

Задание 6. Все левые остаются

Лекарство — LEFT JOIN: та же выборка, но Ника возвращается, и в колонке гильдии у неё NULL (читать через is_null — №6!). Проговорите разницу словами: JOIN — «покажи пары», LEFT JOIN — «покажи всех слева, и пару, если есть». Эталон полигона: Борис, не записанный ни в один кружок, виден только в LEFT JOIN.

Задание 7. Сирота проходит молча

Проверка обещания урока: объявите FOREIGN KEY и вставьте игрока с guild_id = 999 (такой гильдии нет!) — вставится без единого слова (проверено). Более того: попробуйте включить проверку — PRAGMA foreign_keys = ON — и убедитесь, что в нашей версии она не срабатывает (сирота проходит снова, чтение прагмы даёт 0). Вывод честный и инженерный: FOREIGN KEY здесь — документация замысла, а сторожем работает ваша программа (проверка существования перед вставкой — bind-SELECT из №4!). В настоящей SQLite прагма включает контроль; знать разницу между «объявлено» и «проверяется» — важнее, чем уметь писать само объявление.

Задание 8. Забыл условие

Страшный опыт, который стоит пережить в учебной базе: SELECT ... FROM players JOIN guilds без ON (или с условием, соединяющим не то). Посмотрите на число строк: 10 героев × 2 гильдии = 20 строк — каждый с каждым! Это «декартово произведение»: без условия база честно соединяет всё со всем. На больших таблицах такой запрос вешает сервер (миллион × миллион!). Диагноз: строк стало неожиданно много → проверь ON; и привычка: писать ON сразу после JOIN, не откладывая.

Блок 3. Аналитика связей

Практика с преподавателем

Задание 9. Кто сколько потратил

У доски — JOIN встречается с GROUP BY (№10!): соединить покупки с товарами, сгруппировать по герою и просуммировать цены:

SELECT p.name AS hero, COUNT(*) AS n, SUM(i.price) AS spent
FROM purchases AS pu
JOIN players AS p ON pu.player_id = p.id
JOIN items AS i ON pu.item_id = i.id
GROUP BY p.name
ORDER BY spent DESC;

Эталон: Ника — 4 покупки на 2999, Лея — 3 на 2177, Мира — 3 на 1650. Проговорите: сначала соединяем, потом группируем — база сперва собирает строки-пары, потом считает по группам. Именно так строятся все настоящие отчёты: «выручка по клиентам», «оценки по ученикам», «часы по проектам» — везде JOIN плюс агрегат.

Самостоятельная практика

Задание 10. Топ товаров

Обратная сторона: какие товары покупают чаще всего (JOIN purchases с items, GROUP BY названию, COUNT). И второй вопрос: какой товар принёс больше всего золота (COUNT × цена — или SUM цены, что тут одно и то же: почему?). Аналитика лавки: спрос против выручки — не одно и то же, и дорогой редкий товар может обойти популярную мелочь.

Задание 11. Сторож связи

Раз база не проверяет — проверим сами (з.7!). Программа-приёмщик покупки: спросить id героя и id товара → проверить существование обоих (два bind-SELECT-а) → если чего-то нет, вежливый отказ («героя 99 не существует»); если всё на месте — вставить в транзакции (№8!). Это и есть «сторож связи», который в других базах делает FOREIGN KEY. Проверьте оба сценария.

Задание 12. Ревизия сирот

Диагностика существующих данных — фирменный жанр раздела: найти покупки, чей player_id не соответствует ни одному герою. Одним запросом: LEFT JOIN players ON ... WHERE players.id IS NULL (гениальный узор: соединяем, оставляем всех левых — и берём тех, кому пары не нашлось!). Эталон полигона ловит запись, ссылающуюся на ребёнка 99. Сравните с перебором из №12 (заметка з.16) — там нужен был цикл в цикле, тут одна строка SQL. LEFT JOIN + IS NULL = поиск непарных — запомните этот узор, он пригодится всюду.

Минутка из внешнего мира. Почему таблицы делят

Это не задание — делать ничего не нужно. Просто любопытное из большого мира, читается за минуту.

Разделение данных по таблицам называется нормализацией, и придумал её в 1970 году Эдгар Кодд — тот самый человек, с чьей статьи началась вся эпоха реляционных баз. Идея простая: каждый факт хранится ровно один раз. Если название гильдии лежит в тысяче строк, то однажды в девятистах девяноста девяти оно будет «Explorers», а в одной — «Exploreres», и никто не поймёт, что это одна гильдия. Такие расхождения называют аномалиями, и нормализация от них лечит. Но у медали есть оборот: чем больше таблиц, тем больше JOIN-ов в каждом запросе, а JOIN — работа. Поэтому в аналитических системах иногда делают наоборот — денормализуют: сознательно дублируют данные, чтобы отчёты строились быстрее. Взрослый инженер выбирает между «хранить один раз и соединять» и «продублировать и читать быстро», понимая цену обоих решений. Вы теперь тоже: в третьей книге вы страдали от чисел вместо имён, а сегодня узнали, чем платят за красоту неповторяющихся данных.

Блок 4. Сцены с управлением

Задание 13. Отчёт по клиентам

Полноценный аналитический отчёт по guild.db: по каждому герою — сколько покупок, на какую сумму, самый дорогой купленный товар (MAX цены в группе!), и доля в общей выручке лавки (второй запрос + арифметика — №10 з.19-навык). Отсортировать по тратам. Ника с её 2999 возглавит список — покажите отчёт как есть, он говорит сам за себя.

Задание 14. Расписание кружков

Обратный скаффолд: «Три таблицы: kids (id, name), clubs (id, title, teacher), memberships (id, kid_id, club_id) — связь "многие ко многим": один ребёнок ходит в несколько кружков, в кружке — несколько детей. Наполнить; вывести:

  1. кто где занимается — тройной JOIN с именами и учителями
  2. сколько человек в каждом кружке (JOIN + GROUP BY)
  3. кто не ходит никуда (LEFT JOIN + COUNT = 0!)».

Соберите. Связь «многие ко многим» через промежуточную таблицу — самая частая схема в мире: ученики и курсы, актёры и фильмы, товары и заказы.

Задание 15. Справочник вместо повторов

Рефакторинг данных: возьмите таблицу, где класс героя записан текстом в каждой строке (как в guild.db!), и разделите: справочник классов (id, title) + ссылка class_id в героях. Программа: создать справочник из DISTINCT-значений (№10!), заполнить его, обновить героев (UPDATE ... WHERE class = ...), показать результат через JOIN — вывод не изменился, а данные стали чище. И вопрос-обсуждение: стало лучше или сложнее? (Правильный ответ: смотря зачем — минутка объяснила обе стороны.)

Задание 16. Кто с кем не пересекался

Хитрая аналитика на LEFT JOIN: найти пары «герой — товар», которых не было в покупках (герой ни разу не покупал этот товар). Полный перебор пар делается... сложно (нужны все сочетания). Упростим: для одного выбранного товара найти всех героев, которые его не покупали (LEFT JOIN покупок этого товара + IS NULL — узор з.12!). «Кому предложить новинку» — так работают рекомендации в магазинах: ищут не то, что купили, а то, чего не купили.

Блок 5. Полигон

Задание 17. База школьных кружков

Финальный полигон раздела — полная система «многие ко многим» (эталон прогнан!): схема — kids, clubs, memberships со всеми ограничениями (PRIMARY KEY, UNIQUE названий, NOT NULL); наполнение скриптом или конвейером, включая одну нарочную сироту (запись на несуществующего ребёнка 99); отчёты: кто где занимается (тройной JOIN — «Мира → Робототехника (Пётр Ильич)»), сколько кружков у каждого (LEFT JOIN — «Борис нигде не занимается!»), популярность кружков (LEFT JOIN + COUNT, включая пустые кружки!), ревизия сирот (LEFT JOIN + IS NULL — находит запись на ребёнка 99); действия: записать ребёнка в кружок со сторожем связи (з.11), отчислить из кружка. Сдача: полный отчёт + устный экзамен по трём вопросам: чем JOIN отличается от LEFT JOIN, почему сирота вставился, и что будет с отчётом, если забыть ON.

Задание 18 ⭐. Витрина магазина

Настоящий интерфейс на связях: программа-магазин по guild.db (копию сделайте — правки!): каталог — товары с числом покупок (LEFT JOIN — товары, которые никто не купил, тоже показать с нулём!); карточка героя — его имя, золото и список покупок с названиями и ценами (JOIN), плюс «потрачено всего»; покупка — выбрать героя и товар по id, проверить связи (з.11) и хватает ли золота, в транзакции списать монеты и записать покупку (№8!); топ покупателей (з.9). Пять экранов, три таблицы, все инструменты раздела разом. Это уже маленькое приложение, а не упражнение.

Задание 19 ⭐⭐. Аудит целостности

Финальная звезда раздела — инструмент, проверяющий базу целиком. Программа-аудитор по любой вашей базе со связями:

  1. сироты — по каждой связи найти записи, чьи ссылки никуда не ведут (LEFT JOIN + IS NULL — з.12), с отчётом «memberships: 1 сирота (kid_id = 99)»
  2. осиротевшие справочники — записи справочника, на которые никто не ссылается («кружок "Шахматы": ни одного участника» — LEFT JOIN в обратную сторону!)
  3. дубли — повторяющиеся пары в связующей таблице (один ребёнок дважды записан в один кружок — GROUP BY kid_id, club_id HAVING COUNT(*) > 1 — №10!)
  4. итоговый вердикт — «база здорова» или список бед с числами
  5. лечение по требованию — удалить сирот и дубли (в транзакции, с подтверждением!).

Прогоните на нарочно испорченной базе и на чистой. Такой аудитор — реальная утилита, которую пишут в каждом проекте с данными: базы портятся от старых багов, ручных правок и незавершённых операций, и кто-то должен уметь это находить. Кто добавит режим «только показать, ничего не менять» (dry-run из №11!) — тот сделал инструмент, которому можно доверить рабочую базу.
