Каждое приведённое сообщение Idyllium — дословный вывод среды выполнения,
снятый с пробной программы. **Все три колонки сравнения проверены тем же
способом**: Qt 5 `QtSql` с драйвером `QSQLITE`, CPython 3.12 со стандартным
модулем `sqlite3`, Node 22 с `node:sqlite`. Всякое значение, помеченное словом
«проверено», — снятый вывод, и это верно для каждой колонки.

QtSql выбран вместо сырого C-API sqlite3 сознательно. Курс C++, доходящий
до баз данных, почти всегда уже дошёл до Qt — часть 2 серии сравнивает год
виджетов с Qt Widgets, — поэтому `QSqlQuery` и есть то, что ученик реально
встречает. Так и честнее: C-API это драйвер, а не учебный интерфейс, и упрекать
его в неснисходительности бессмысленно. QtSql — высокоуровневая привязка,
построенная для прикладных программистов, как и две другие, и ломается она
интереснее.

## 0. Что меняется, когда начинается тема баз данных

Тема JSON (часть 5) уже сломала удобное правило «всякое значение рождается
внутри программы»: текст приходил снаружи, и его форма была неизвестна
до времени выполнения. База данных ломает ещё три правила сразу.

1. **Данные переживают программу.** Ошибка не исчезает по завершении
   процесса — она уже записана в файл, который прочитает следующий запуск.
   Тихая неверная запись это не неверный вывод, это *долговременный ущерб*.
2. **Инструкции — это текст.** SQL это второй язык, вложенный строковыми
   литералами, и язык-хозяин не может проверить в нём ни слова. Опечатка
   в имени столбца не является ошибкой компиляции нигде в этом сравнении.
3. **У результата нет объявленной формы.** `SELECT` возвращает строки, чьи
   столбцы названы запросом, а не каким-либо объявлением. Спросить не тот —
   самый частый промах темы.

Всё ниже — вариации одного вопроса: **когда запрос, строка, столбец или
значение не такие, как предполагал код, узнаёт ли об этом ученик?**

Есть и четвёртая перемена, которую легко проглядеть и которая порождает самую
вредную ошибку новичка во всей серии: **некоторые привязки не сохраняют ваши
данные, пока им об этом не скажут.** См. §10.

## 1. Как читать разборы

Форма та же, что в частях 1–5:

- **Ребёнок пишет** — правдоподобный код новичка.
- **Что делают другие привязки** — по строке на экосистему, с классом
  поведения:
  - **ТИХО** — неверный или неожиданный результат без диагностики. Опасный
    класс.
  - **ГРОМКО** — отказывается или падает с сообщением.
  - **НЕВНЯТНО** — ошибка есть, но сообщение новичку не расшифровать.
  - **ПРЕДУПРЕЖДАЕТ** — печатает предупреждение в stderr, а затем
    **возвращает правдоподобное значение и продолжает**. Этот класс нужен ради
    QtSql: текст `qWarning` попадает в поток, которого ученик, запускающий
    программу из среды, может никогда не увидеть, а программа тем временем
    несёт дальше ноль или пустую строку как ни в чём не бывало.
  - **ОК** — ведёт себя так, как ждёт человек.
- **Ответ Idyllium** — с дословным сообщением.

Замечание о справедливости: все три привязки сравнения — добротные взрослые
инструменты, созданные перевозить данные в приложениях, написанных
профессионалами. Некоторые перечисленные ниже как беды поведения в этой
обстановке защитимы: Qt возвращает недействительный `QVariant`, а не бросает
исключение, потому что Qt в целом избегает исключений. Вопрос здесь
по-прежнему узкий: *что это делает с двенадцатилетним, у которого в первой
таблице четыре строки?*

## 2. Открытие базы

**Ребёнок пишет** `sqlite.open("players.db")` и ждёт либо базу, либо
объяснение.

| Экосистема | Поведение | Подробности |
|---|---|---|
| C++ (QtSql) | **ТИХО** | Проверено: `open()` по пути, чьего каталога не существует, возвращает `false` и не печатает ничего; текст (`unable to open database file Error opening database`) живёт только внутри `lastError()`. Программа, игнорирующая `bool`, едет дальше, и первый же запрос печатает в stderr `QSqlQuery::exec: database not open` и отдаёт `0`. Отдадим должное: опечатка в имени **драйвера** ловится хорошо — в stderr идёт `QSqlDatabase: QSQLTIE driver not loaded`, а следом `QSqlDatabase: available drivers: QSQLITE` (проверено). |
| Python | ГРОМКО | `sqlite3.connect(path)` поднимает `OperationalError: unable to open database file` — точно, хотя и не говорит, *почему* (нет каталога, нет прав). |
| JavaScript | ГРОМКО | `new DatabaseSync(path)` бросает с сообщением SQLite. |
| **Idyllium** | **ГРОМКО** | `runtime error: sqlite.open() cannot open 'нет/такой/папки/x.db': parent directory does not exist: нет/такой/папки` |

Сообщение Idyllium называет конкретную причину. Это важнее, чем кажется:
«unable to open database file» отправляет ученика проверять написание и права
доступа, тогда как настоящая беда — папка, которую никто не создал.

Открытие несуществующего файла его **создаёт** — во всех экосистемах здесь.
Так ведёт себя SQLite, это правильно, и это означает, что опечатка в имени
файла порождает вторую, пустую базу вместо ошибки, — см. §15.

Заметьте также, чего сообщение Idyllium *не* требует: ни строки драйвера,
ни реестра соединений. `sqlite.open(path)` возвращает базу или останавливает
программу; нет ни `bool`, который можно забыть, ни второго вызова, чтобы
добраться до текста.

## 3. Инструкция, которая не разбирается

**Ребёнок пишет** `SELEKT` — или забывает запятую между столбцами.

| Экосистема | Поведение | Подробности |
|---|---|---|
| C++ (QtSql) | **ТИХО** | Проверено: `q.exec("SELEKT 1")` возвращает `false` и не печатает ничего. Текст доступен, если спросить, — `lastError().text()` даёт `near "SELEKT": syntax error Unable to execute statement`, — но программа, которая не спрашивает, просто продолжает, а следующий `q.next()` и затем `q.value(0).toInt()` дают `0` (проверено). |
| Python | ГРОМКО | `OperationalError: near "SELEKT": syntax error` (проверено) |
| JavaScript | ГРОМКО | `Error: near "SELEKT": syntax error` (проверено) |
| **Idyllium** | **ГРОМКО** | `runtime error: sqlite execution failed: near "SELEKT": syntax error` |

Все три высокоуровневые привязки пропускают собственное сообщение SQLite
насквозь, а сообщения SQLite хороши. Idyllium добавляет перед ним название
операции, чтобы ученик с одного взгляда отличал жалобу базы от жалобы языка.

То же и со столбцом, которого нет в запросе:
`runtime error: sqlite execution failed: no such column: nmae`.

## 4. Как достать значения из строки

**Ребёнок пишет** цикл по `SELECT name, level FROM players` и читает два
столбца.

| Экосистема | Поведение | Подробности |
|---|---|---|
| C++ (QtSql) | **ТИХО** | `query.value(0)`, `query.value(1)` — **по индексу**, и именно эту форму показывает каждое руководство. Добавьте столбец в начало `SELECT` — и все индексы сдвинутся; программа продолжит работать и будет читать не те данные. Доступ по имени существует (`query.value("name")`), стоит поиска на каждый вызов и остаётся дорогой, по которой ходят реже. |
| Python | **ТИХО** | Строки по умолчанию кортежи (проверено: `('Мира', 7)`), поэтому доступ идёт как `row[0]`, `row[1]` — та же ловушка сдвига индексов. Именованный доступ есть (`conn.row_factory = sqlite3.Row`), но его надо включить, и ни одно руководство не доберётся до него раньше, чем ученик напишет двадцать позиционных чтений. |
| JavaScript | ОК | `node:sqlite` возвращает объекты с именованными столбцами (проверено: `{ name: 'Мира', level: 7 }`). Хорошее умолчание. |
| **Idyllium** | **ОК** | Доступ только по имени столбца: `rows.get_string("name")`, `rows.get_int("level")` |

Позиционного геттера в API Idyllium нет вовсе. `column_name(index)`
и `column_count()` существуют для программ, которым надо разглядеть незнакомый
результат, но обычный путь позиционно не записывается, и ошибке сдвига
индексов негде жить. Добавление столбца в `SELECT` не может молча изменить то,
что читает уже написанная строка.

## 5. Строки, которой нет

**Ребёнок пишет** поиск игрока, которого ещё не создали.

| Экосистема | Поведение | Подробности |
|---|---|---|
| C++ (QtSql) | **ПРЕДУПРЕЖДАЕТ** | Проверено: чтение до `next()` печатает в stderr `QSqlQuery::value: not positioned on a valid record` и возвращает **недействительный `QVariant`**, чей `toString()` даёт `""`, а `toInt()` — `0`. Программа продолжает с этими значениями. `isValid()` сказал бы правду, но спрашивать никто не обязан. |
| Python | **ТИХО** | `cur.fetchone()` возвращает `None` (проверено). Программа продолжает; отказ всплывает позже как `TypeError: 'NoneType' object is not subscriptable`, в строке, которая не является причиной. |
| JavaScript | **ТИХО** | `stmt.get()` возвращает `undefined` (проверено). Тот же отложенный отказ по неверному адресу, что и с `None`. |
| **Idyllium** | **ГРОМКО** | `runtime error: sqlite result has no current row; call next() first` |

Результат в Idyllium начинается *до* первой строки и отвергает любой геттер,
пока `next()` не был вызван и не вернул `true`. Поэтому идиома — тот же цикл
`while`, который ученик уже пишет для файлов, а пустой случай обрабатывается
тем, что тело цикла просто не выполняется:

```idyllium
    sqlite.Statement find = db.prepare("SELECT name, level FROM players WHERE level > :min");
    find.bind("min", 5);
    sqlite.Result rows = find.execute();
    while (rows.next()) {
        console.writeln(rows.get_string("name"), ": ", rows.get_int("level"));
    }
```

А когда вопросу «нашлось ли хоть что-нибудь» нужен собственный ответ —
сообщение о пустом списке, другая ветка, — результат отвечает прямо,
без сигнальных значений и ничего не тратя:

```idyllium
    if (rows.has_rows) {
        while (rows.next()) { … }
    } else {
        console.writeln("никого нет");
    }
```

`has_rows` истинно, только когда есть хотя бы одна строка; пустой `SELECT`
сообщает `false`, и так же отвечают `INSERT`/`UPDATE`/`DELETE`, у которых для
этого есть `affected_rows`.

У трёх остальных на потоковом пути эквивалента нет, а двое предлагают
именованное свойство, которое выглядит ответом и им не является.
`cursor.rowcount` в Python — **`-1` для каждого `SELECT`**, пустого или нет
(проверено). `query.size()` в QtSql — **`-1` для любого запроса SQLite**,
пустого или нет (проверено): драйвер SQLite не сообщает размеров результата,
и метод документирует это, возвращая одно и то же число и для «ни одной
строки», и для «четырёх строк». В обоих работает материализация всего
результата (`fetchall()` / `.all()`, проверено — дают `[]`, когда ничего
не нашлось) или цикл со счётчиком, что верно, но протаскивает все строки
ради ответа «да или нет».

Итого: ни `None`, ни `undefined`, ни `-1`, ни сигнального значения, похожего
на данные.

## 6. Чтение столбца, которого нет

**Ребёнок пишет** `get_string("nmae")` — опечатку в *читающем* коде, а не
в SQL.

| Экосистема | Поведение | Подробности |
|---|---|---|
| C++ (QtSql) | **ПРЕДУПРЕЖДАЕТ** | Проверено: `value("nmae")` печатает в stderr `QSqlQuery::value: unknown field name 'nmae'` и возвращает недействительный `QVariant` — то есть `""` и `0` дальше по течению. Выход **индекса** за диапазон (`value(5)`) даёт то же самое. В обоих случаях программа оставляет себе ноль и едет дальше. |
| Python | ГРОМКО | С кортежами `row[5]` поднимает `IndexError`; с `sqlite3.Row` `row["nmae"]` поднимает `IndexError: No item with that key`. |
| JavaScript | **ТИХО** | `row.nmae` — это `undefined` (проверено): обычный промах по свойству объекта, неотличимый от столбца, который существует и содержит NULL. |
| **Idyllium** | **ГРОМКО** | `runtime error: sqlite result has no column 'nmae'` |

Обратите внимание на различение, которое Idyllium держит, а JavaScript теряет:
**отсутствующий столбец** и **столбец со значением NULL** — разные ситуации
с разными сообщениями (`has no column 'nmae'` против
`column 'a' is null, expected int`). В JS и то и другое — `undefined`.

## 7. Неверный тип и NULL

**Ребёнок пишет** `get_int` для столбца, в котором лежит текст, или для
столбца, в котором лежит NULL.

| Экосистема | Поведение | Подробности |
|---|---|---|
| C++ (QtSql) | **ТИХО** | Проверено, и это флагман QtSql: `value(0).toInt()` на тексте `"Mira"` возвращает **`0` вообще без предупреждения** — даже без той строки в stderr, которую получают два предыдущих случая. На NULL тоже возвращает `0` (проверено). Два разных отказа и один неотличимый ответ, ровно как в сыром C-API под ним. |
| Python | **ТИХО** | Значения приходят родными типами, поэтому текстовый столбец просто *является* `str`, а NULL просто *является* `None` (проверено и то и другое). Несовпадение всплывает на первом операторе, который его отвергнет, далеко от чтения. |
| JavaScript | **ТИХО** | То же: свойство оказывается строкой или `null`, а арифметика над ним делает то, что делает арифметика JavaScript. |
| **Idyllium** | **ГРОМКО, дважды и по-разному** | `runtime error: sqlite column 'b' is text, expected int` · `runtime error: sqlite column 'a' is null, expected int` |

Оба сообщения называют столбец, что в нём лежит и что спросили. У `get_bool`
свой точный отказ, потому что логического типа в SQLite нет:
`runtime error: sqlite column 's' is text, expected bool (integer 0 or 1)`.

Когда столбца действительно может не быть, проверка явная и читается вопросом —
той же формы, что `json.Object.has()` в части 5:

```idyllium
    if (rows.is_null("level")) { ... } else { int level = rows.get_int("level"); }
```

`sqlite.Value` (из `rows.get("column")`) — это форма, допускающая NULL,
с `is_null()`, `is_int()`, `is_float()`, `is_string()` и парными
преобразователями `to_*`; она зеркалит `json.Value`, чтобы ученик выучил одну
форму для обоих.

## 8. Параметры и вопрос, на который обязан ответить каждый курс

**Ребёнок пишет** строку поиска и вклеивает текст прямо в запрос.

Это единственная тема, где разница между экосистемами не в диагностике,
а в том, **как выглядит обычный путь**.

| Экосистема | Формы параметров | Замечания |
|---|---|---|
| C++ (QtSql) | `?` и `:name` | Две схемы бок о бок: `addBindValue()` заполняет `?` по порядку, `bindValue(":name", …)` — по имени (обе проверены в работе). Смешивать их в одном запросе — задокументированная ошибка, а какой воспользуется ученик, зависит от того, какое руководство он открыл. |
| Python | `?` и `:name` | Документация первым показывает `?`; параметры подаются кортежем, порядок которого обязан совпадать. |
| JavaScript | `?` и именованные | `?` — обычная форма в примерах; подаются позиционными аргументами. |
| **Idyllium** | **только `:name`** | `?`, `@name` и `$name` отвергаются: `runtime error: unsupported SQLite parameter '?'; use named parameters such as ':name'` |

У любой позиционной схемы параметров тот же отказ, что и у позиционного
доступа к столбцам (§4): правите инструкцию, забываете переставить аргументы —
и значения уезжают не в те столбцы без единого слова. Idyllium убирает саму
схему, а не предупреждает о ней: способ написать параметр ровно один, и он
несёт собственное имя:

```idyllium
    sqlite.Statement find = db.prepare(
        "SELECT name, level FROM players WHERE level >= :min ORDER BY level"
    );
    find.bind("min", 5);
    sqlite.Result rows = find.execute();
```

Опечатка в имени ловится, и сообщение показывает параметр так, как его пишет
SQL: `runtime error: sqlite statement has no parameter ':nmae'`.

По вопросу безопасности честная формулировка коротка: **вклеивание
пользовательского текста в SQL здесь по-прежнему возможно, как и в любой
экосистеме этого сравнения** — `db.execute("… WHERE name = '" + typed + "'")`
это обычная склейка строк, и запретить её не может ни один язык. API делает
другое: правильный путь короче неправильного и записывается единственным
способом, так что «пользуйся `:name`» становится правилом без исключений.
Курс преподаёт его как правило *прежде всего о корректности*: имя
с апострофом ломает склеенный запрос сразу, задолго до того, как кто-нибудь
упомянет злоумышленников.

## 9. Непривязанный параметр

**Ребёнок пишет** `INSERT` с двумя параметрами и привязывает один — обычно
после того, как добавил столбец и забыл второй `bind`.

| Экосистема | Поведение | Подробности |
|---|---|---|
| C++ (QtSql) | **ТИХО, и хуже** | Проверено: непривязанный `:level` становится NULL, `exec()` возвращает `true`, `lastError()` **пуст**, и наполовину заполненная строка записывается. Хуже того, **опечатка в имени подстановки** — `bindValue(":nmae", …)` для запроса, объявившего `:name`, — молча игнорируется, поэтому настоящий параметр остаётся непривязанным и тоже становится NULL, а `exec()` снова возвращает `true` (проверено). Оба случая ловит только столбец с `NOT NULL`. |
| Python | ГРОМКО | `ProgrammingError: Incorrect number of bindings supplied. The current statement uses 2, and there are 1 supplied.` (проверено) — считает их, но не называет. |
| JavaScript | **ТИХО** | Проверено: `run("X")` против двух подстановок `?` **сработал**, вставив `{ id: 1, name: 'X', level: null }`. Ловит только ограничение `NOT NULL`, и только если автор схемы его написал. |
| **Idyllium** | **ГРОМКО, по имени** | `runtime error: sqlite statement has unbound parameter ':level'` |

Это пункт, в котором долговременный ущерб получить проще всего: две из трёх
привязок сравнения с готовностью запишут полупустую строку в файл, который
переживёт программу, а ученик обнаружит это через неделю, когда отчёт окажется
неверным. Idyllium отказывается до записи и называет забытый параметр.

Привязки сохраняются после `execute()`, чтобы подготовленную инструкцию можно
было переиспользовать в цикле; `clear_bindings()` нарочно начинает новый
набор.

## 10. Транзакции и забытый `commit`

**Ребёнок пишет** программу, которая вставляет три строки и завершается.

| Экосистема | Поведение | Подробности |
|---|---|---|
| C++ (QtSql) | ОК | Автофиксация включена; голый `INSERT` долговечен сразу. `transaction()`/`commit()`/`rollback()` возвращают `bool`, и проверено: `commit()` без открытой транзакции возвращает `false`, оставляя `lastError()` **пустым**, — отказ, в котором нет слов. |
| Python | **ТИХО — худший пункт этого документа** | Модуль открывает неявную транзакцию перед изменяющими операциями и **откатывает её, если соединение закрывается без `commit()`**. Проверено: создать таблицу, вставить строку, `close()` — файл есть, таблица есть, а строки **нет**, и нигде ни сообщения. `CREATE TABLE` уцелел (DDL фиксируется неявно), поэтому программа выглядит сработавшей. |
| JavaScript | ОК | `node:sqlite` работает в автофиксации; голый `INSERT` долговечен. |
| **Idyllium** | **ОК** | Автофиксация; проверено двумя отдельными запусками — строки, записанные первой программой, читаются второй, и никакого `commit()` нигде |

Поведение Python заслуживает отведённого ему места из-за того, *чему оно
учит*. Картина мира ученика — «программа сделала дело, значит, дело сделано» —
верна во всех остальных частях курса и здесь молча ложна. Обычная первая
встреча — база с домашним заданием, пустая в понедельник, а обычный вывод,
который делает ученик, — «базы данных ненадёжны».

Явные транзакции в Idyllium есть и проверяются на каждом шаге:

```idyllium
    db.begin_transaction();
    db.execute("UPDATE acc SET money = money - 100 WHERE name = 'Аня'");
    db.execute("UPDATE acc SET money = money + 100 WHERE name = 'Боря'");
    db.commit();                       // или db.rollback();
```

| Ошибочное употребление | Сообщение |
|---|---|
| `commit()` без открытой транзакции | `runtime error: sqlite database has no active transaction to commit` |
| `begin_transaction()` дважды | `runtime error: sqlite database already has an active transaction` |

`conn.commit()` в Python без открытой транзакции — молчаливая пустышка
(проверено). Оба сообщения Idyllium — отказы, потому что оба написания
означают, что автор потерял след состояния, — а потеря следа транзакции это
и есть способ, которым деньги исчезают с одного счёта, не появившись
на другом.

Одна оговорка, полностью изложенная в §15: транзакция, **открытая
и не завершённая**, откатывается при завершении программы, молча. Это
правильное поведение базы данных, и это единственное место, где Idyllium может
потерять запись, не сказав ни слова, — но для этого ученик должен был открыть
транзакцию нарочно, тогда как в Python это путь по умолчанию.

## 11. Целые на краю диапазона

`INTEGER` в SQLite — знаковое 64-битное значение. Языки-хозяева расходятся
в том, что происходит на этой границе.

| Экосистема | Поведение | Подробности |
|---|---|---|
| C++ (QtSql) | **ТИХО** | Проверено: `9007199254740993`, записанное и прочитанное через `toLongLong()`, точно, — но `toInt()` на том же значении возвращает **`1`**, младшие 32 бита, без предупреждения. Правильный метод существует и длиннее на одну букву; ошибка в выборе стоит всего числа. |
| Python | ОК | Целые произвольной точности; `9223372036854775807` переживает рейс (проверено). За пределами 64 бит вставка поднимает `OverflowError: Python int too large to convert to SQLite INTEGER` (проверено). |
| JavaScript | ГРОМКО | Проверено: чтение `9007199254740993` бросает `RangeError: Value is too large to be represented as a JavaScript number`. Отказ лучше порчи — здесь `node:sqlite` ведёт себя лучше, чем `JSON.parse` в части 5. |
| **Idyllium** | **ОК, а потом ГРОМКО на настоящей границе** | `9007199254740993` переживает рейс точно; значение за пределами 64 бит отвергается на входе |

```text
runtime error: sqlite cannot store 123456789012345678901234567890: the value is
outside the INTEGER column range (types.int64)
```

Сообщение стоит прочитать дважды. Собственный `int` в Idyllium точен при любом
размере (часть 5, §5), поэтому здесь у языка место не кончилось — здесь язык
замечает, что **столбец** не вместит предлагаемое, и говорит, о какой предел
споткнулись. `get_int64()` и `to_int64()` доступны там, где важен полный
64-битный диапазон.

## 12. Время жизни: после `close`

**Ребёнок пишет** строку уборки не в том порядке.

| Экосистема | Поведение | Подробности |
|---|---|---|
| C++ (QtSql) | **ПРЕДУПРЕЖДАЕТ / ТИХО** | `QSqlQuery` владеет своими ресурсами и убирает их в деструкторе, поэтому семейство висячих указателей из C-API исчезло. Осталось более тихое. Проверено: после `finish()` `value(0).toInt()` даёт `0` и строку `QSqlQuery::value: not positioned on a valid record` в stderr. После `db.close()` уже добытая строка по-прежнему читается верно (`7`, действительна — Qt её сохранил), а **новый** `exec()` возвращает `false`, печатает в stderr `QSqlQuery::exec: database not open` и оставляет `lastError()` **пустым**, — то есть единственный след находится в потоке, а не в объекте, который вы стали бы спрашивать. |
| Python | ГРОМКО | `ProgrammingError: Cannot operate on a closed database.` |
| JavaScript | ГРОМКО | Бросает при использовании после `close()`. |
| **Idyllium** | **ГРОМКО, на каждый объект** | `sqlite database is already closed` · `sqlite statement is already closed` · `sqlite result is already closed` |

Три разных предложения для трёх разных объектов, чтобы ученик узнавал,
*что именно* он закрыл слишком рано, а не только *что* что-то закрыто.

Сознательное решение, проверенное пробой: **результат переживает инструкцию,
которая его породила.** Результаты — буферизованные снимки, поэтому вот так
законно и полезно:

```idyllium
    sqlite.Statement st = db.prepare("SELECT name FROM p ORDER BY id");
    sqlite.Result r = st.execute();
    st.close();                 // инструкции больше нет
    while (r.next()) { ... }    // результат по-прежнему работает
```

— и, как и собственное управление ресурсами в `QSqlQuery`, это целиком
убирает семейство ошибок с висячими указателями ценой того, что строки
держатся в памяти.

## 13. Программа целиком

Всё вышеописанное в той форме, которую ученик действительно пишет. Проверено
от начала до конца:

```idyllium
use console;
use sqlite;

main() {
    sqlite.Database db = sqlite.open("players.db");
    db.execute(
        "CREATE TABLE IF NOT EXISTS players (" +
        "id INTEGER PRIMARY KEY AUTOINCREMENT, " +
        "name TEXT NOT NULL, level INTEGER NOT NULL)"
    );

    sqlite.Statement insert = db.prepare(
        "INSERT INTO players (name, level) VALUES (:name, :level)"
    );
    insert.bind("name", "Мира");
    insert.bind("level", 7);
    sqlite.Result added = insert.execute();
    console.writeln("добавлено строк: ", added.affected_rows,
                    ", id ", added.last_insert_id.to_int());
    insert.close();

    sqlite.Result rows = db.execute("SELECT name, level FROM players ORDER BY id");
    while (rows.next()) {
        console.writeln(rows.get_string("name"), ": ", rows.get_int("level"));
    }
    rows.close();
    db.close();
}
```

Ничего из этого не является церемонией привязки. Ни имени драйвера строкой,
ни реестра соединений, которое надо назвать и потом убрать, ни возвратов
`bool`, которые не с чем сравнивать, ни объекта-курсора отдельно
от соединения, ни `row_factory`, который надо настроить, чтобы у столбцов
появились имена. `affected_rows` и `last_insert_id` — свойства результата той
инструкции, которая их и породила, а не соединения, поэтому две вставки
в цикле не могут сообщить чужой идентификатор.

Во что те же девять строк обходятся в других местах, если считать *то, что
надо выучить до появления первой строки*:

| Экосистема | До того, как первый `SELECT` что-нибудь напечатает |
|---|---|
| C++ (QtSql) | `QSqlDatabase::addDatabase("QSQLITE")` — имя драйвера, записанное строкой; имена соединений и их время жизни; `open()`, возвращающий `bool`; `QSqlQuery`, привязанный к соединению; `QVariant` и вопрос, какой `to*()` вызвать; `lastError().text()` как единственный способ увидеть, что пошло не так |
| Python | `connect` → `cursor` → `execute` → `fetchone`, четыре объекта на один вопрос; строки-кортежи, пока не обнаружен `row_factory`; и `commit()`, отсутствие которого теряет данные (§10) |
| JavaScript | `new DatabaseSync(path)`, `prepare`, а затем выбор между `run`/`get`/`all`, который решает, получите вы одну строку, все строки или сводку |

вместо пропажи, `undefined` вместо обоих), где она **адресует данные
по позиции** (индексы столбцов, порядок параметров) и где она **откладывает
долговечность до вызова, о котором ученик не знает**. Ответ Idyllium в каждом
случае один и тот же: ничто не адресуется по позиции, ни одно отсутствие
не отвечается значением, и ничто не откладывается.

## 15. Честный остаток: чего SQLite в Idyllium по-прежнему не ловит

1. **Сродство типов в SQLite остаётся сродством типов SQLite.** Проверено:
   привязка строки `"не число"` в столбец, объявленный `INTEGER`, сохраняет её
   текстом (`typeof` даёт `text`), молча, ровно как в трёх остальных
   экосистемах. Объявленные типы столбцов в SQLite носят рекомендательный
   характер, и API этого не изменит. Ответ — ограничения `CHECK` в схеме,
   и место им в учебных материалах про схемы, а не про привязку.
2. **Транзакция, открытая и не завершённая, откатывается при выходе, молча.**
   Проверено: `INSERT` внутри `begin_transaction()` без `commit()` и без
   `close()` оставляет файл неизменным. Это правильное поведение базы данных
   и зеркальное отражение умолчания Python (§10) — но это молчаливая потеря
   записи, и материал, преподающий транзакции, обязан на том же дыхании
   преподать `commit()` и `rollback()`.
3. **Пользовательский текст, вклеенный в SQL, остаётся SQL.** API не может
   запретить склейку строк. `:name` короток, записывается единственным
   способом и защищён от альтернатив — это самое сильное, что может сделать
   привязка; остальное — преподавание.
4. **Опечатка в имени файла создаёт новую пустую базу.** `sqlite.open` —
   это «создать или открыть», как у любого инструмента SQLite. Первый запуск
   с ошибочным путём срабатывает и возвращает ноль строк на любой запрос.
   Ничто не предупреждает.
5. **Схему никто не проверяет.** `SELECT`, называющий существующий столбец,
   который означает другое; `JOIN` по неверному ключу; `WHERE`, всегда
   истинный, — всё это корректный SQL, и всё молча. Тот же смысловой остаток
   назван в каждой части серии.
6. **Типа BLOB пока нет, точек сохранения нет, вложенных транзакций нет.**
   Задокументированные ограничения первой версии API, а не случайности.

## 16. Правила для ИИ, пользующегося этим файлом

1. **Пользуйтесь `has_rows`, когда «ничего не нашлось» требует отдельной
   ветки**, и обычным циклом `while (rows.next())`, когда не требует.
   Не порождайте обходов со флагом-счётчиком
   (`bool found = false; while (…) { found = true; … }`): результат отвечает
   на вопрос сам, и чтение этого ответа ничего не тратит.
2. **Всегда вызывайте `next()` перед любым геттером** и всегда читайте
   столбцы по именам. Позиционного геттера нет; не выдумывайте его.
3. **Всегда пользуйтесь параметрами `:name`** и `bind(...)` без двоеточия.
   Никогда не порождайте `?`, `@name` или `$name` — они отвергаются — и никогда
   не порождайте склейку пользовательского ввода в SQL, даже в примерах
   с пометкой «упрощённо».
4. **Привязывайте каждый объявленный параметр до `execute()`.** Если
   порождённый код привязывает только часть, это ошибка: среда выполнения
   назовёт пропущенный.
5. **Не порождайте `commit()` для обычных вставок.** В Idyllium автофиксация,
   и `commit()` без открытой транзакции — ошибка, а не безобидная привычка,
   принесённая из Python.
6. **Пользуйтесь транзакциями только там, где смысл в атомарности** (переводы,
   пакетный импорт), и всегда сопровождайте `begin_transaction()` вызовом
   `commit()` или `rollback()` на каждом пути наружу.
7. **Закрывайте то, что открыли, по порядку** — результат, инструкцию,
   базу, — но помните, что результат законно переживает свою инструкцию
   (§12), поэтому не порождайте оборонительных повторных выполнений.
8. **Предпочитайте `get_int` / `get_string` / `get_float`, когда тип столбца
   известен**, и `get(...)`, возвращающий `sqlite.Value` с `is_null()`, когда
   столбец действительно может быть пустым. Не заворачивайте геттеры
   в оборонительный код, прячущий сообщение о типе от ученика.
9. **Когда ученик приходит из другой привязки, называйте конкретную ловушку**
   из §14, из которой выросла его привычка. «В Python твои строки были
   кортежами, поэтому добавленный столбец сдвинул всё; здесь ты спрашиваешь
   столбец по имени» учит больше, чем «Idyllium строже», — а пришедшим из Qt,
   а это большинство пришедших из C++, первыми стоит назвать
   `value(0).toInt()`, молча возвращающий `0` для текста (§7), и опечатку
   в `bindValue(":nmae", …)`, которую попросту игнорируют (§9).
10. **Не обещайте отловов из §15**, особенно пунктов про сродство типов
    и про опечатку в имени файла.

## 17. Происхождение сведений

Каталог поведения привязок собран из классных наблюдений на курсах C++,
Python и JavaScript для детей 10–15 лет и организован вокруг тех же пяти
проектных критериев, что части 1–5. **Все три колонки сравнения проверены
прогоном** — Qt 5 `QtSql` через драйвер `QSQLITE`, CPython 3.12 `sqlite3`,
Node 22 `node:sqlite`, — и всякое значение, помеченное словом «проверено»,
это снятый вывод, включая молчаливое переполнение `toInt()` в QtSql,
проигнорированную опечатку в подстановке и `size() == -1`; молчаливую потерю
данных без `commit()` в Python; и результаты по сродству типов, общие для всех
четырёх. Это первая часть серии, все колонки сравнения которой получены
пробами, а не отчасти документарно.

Колонка Idyllium — не мнение: каждое сообщение, каждое значение и каждый
круговой рейс получены прогоном пробной программы через текущий компилятор
и среду выполнения, включая проверку сохранности двумя запусками, откат
транзакции, отказ на целочисленной границе, сообщения о закрытых объектах
и семантику `has_rows` из §5. Когда язык меняется, этот файл должен
перепроверяться тем же способом.
